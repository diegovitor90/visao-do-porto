Capítulo 1. Introdução e objetivos

O Visão do Porto é um piloto acadêmico para apoiar observação de segurança em ambiente portuário. Seu estado implementado combina cadastro administrativo, análise de imagem para localizar pessoas e uma interface demonstrativa. A evolução inclui processamento operacional e revisão humana, sujeitos a validação.

Esta documentação orienta desenvolvimento, integração e apresentação técnica. Descreve o que existe, a direção aprovada e as propostas ainda abertas. Não estabelece autorização de acesso, conformidade legal ou aptidão para operação real.

1.1. Objetivos de qualidade

Objetivo Critério de avaliação

Rastreabilidade

Cada afirmação técnica remete a fonte, teste ou decisão identificada.

Isolamento

Falha de sincronização administrativa não interrompe a visão; cenário futuro a testar.

Integridade

Preservar validações de imagem e diferenciar ausência de evidência de infração.

Evolução

Mudar contratos com revisão e testes; diagramas editáveis junto do código.

Privacidade

1.2. Convenções de estado

  • IMPLEMENTADO: localizado no código da base analisada.

  • EVIDÊNCIA HISTÓRICA: resultado registrado anteriormente; não reexecutado nesta tarefa.

  • APROVADO: decisão arquitetural expressa pelo responsável, ainda podendo exigir implementação.

  • CANDIDATO: código externo inspecionado para possível reutilização; integração não comprovada.

  • PROPOSTO: desenho para discussão; não é tabela, endpoint ou funcionalidade existente.

Nos diagramas, títulos e legendas explicitam o estado. Relação conceitual não implica chave estrangeira entre bancos de serviços diferentes. C4 Container representa aplicação/armazenamento lógico; não afirma implantação em Docker.

2.3. Contradições históricas e precedência

A proposta antiga de Cliente → Spring → FastAPI para transporte da imagem está superada pela decisão aprovada nesta revisão. O ADR-001 registra Java fora do caminho principal dos frames. Preservam-se os documentos antigos como histórico; para a direção arquitetural, usar esta revisão e o ADR.

Capacitacao já existe e registra treinamento realizado por trabalhador. Separar catálogo de cursos e certificações é proposta futura, não pendência de criação de uma classe inexistente. SQL Server tem driver no pom.xml, mas a configuração ativa é H2; não há requisito confirmado para SQL Server.

Capítulo 3. Arquitetura atual e arquitetura-alvo

3.1. Contexto atual

O usuário envia imagem pela interface; um cliente administrativo acessa o Spring. O sistema não possui integração institucional ou validação em porto comprovada.

Figura 1. C4 System Context: sistema atual implementado

3.2. Containers atuais

O React chama /api/v1/vision/*; no desenvolvimento o proxy Vite encaminha para a FastAPI. YOLO11n é uma biblioteca/modelo dentro do processo Python, não outro serviço HTTP. O Spring mantém trabalhadores e capacitações via JPA/H2, separado da análise visual. demo_visual.py é uma demonstração local independente.

Figura 2. C4 Container: estrutura atual; H2 embutido e YOLO no processo

O proxy Vite existe somente no servidor de desenvolvimento. O build estático não configura reverse proxy de produção. Revisões do painel são locais ao navegador; alertas e mapa demonstrativos não são eventos do detector.

3.3. Direção aprovada e componentes candidatos

A captura envia imagens ao processamento Python. O Spring mantém o plano administrativo e poderá publicar/fornecer dados a um sincronizador fora do caminho crítico de vídeo. Metadados e referências operacionais poderão circular conforme contratos futuros; não há aprovação para usar Java como proxy de frames.

Figura 3. C4 Container: direção aprovada e extensões candidatas, ainda não integradas

Os módulos candidatos não são decisão de adoção integral nem compromisso de deploy de todos os processos. Cada projeto Python externo usa pacote app; o runner existente usa processos separados e HTTP para evitar colisões de import. Não incorporar esses pacotes indiscriminadamente no processo da FastAPI atual.

3.5. Armazenamento observado

Spring usa jdbc:h2:mem:visaodoporto, ddl-auto=create-drop e open-in-view=false. Não há persistência administrativa durável confirmada. Identity usa SQLAlchemy e SQLite por padrão; PostgreSQL é configurável, não é banco compartilhado com o Java. Regras, Fusion, Incident e Alerts usam estado em memória. Tracker pode persistir câmeras em JSON; os demais repositórios examinados são em memória. Reiniciar serviços pode perder estado e histórico.

Capítulo 4. Domínio, classes e dados

4.1. Modelo de domínio

Uma detecção localiza uma pessoa; não estabelece identidade administrativa. Uma capacitação válida não concede autorização de acesso. Um EPI atribuído a um trabalhador não comprova uso visual. Um alerta comunicado não substitui avaliação, evidência ou decisão humana.

Figura 4. Domínio conceitual: existente e proposto, sem impor banco único

4.2. Classes Java implementadas

Há duas entidades JPA nesta base. Capacitacao possui associação obrigatória ManyToOne(fetch=LAZY) com Trabalhador, FK trabalhador_id e índice composto por trabalhador/código. Vários registros do mesmo código são permitidos. A entidade Trabalhador não declara uma coleção inversa de capacitações.

Figura 5. UML: entidades e serviços Java efetivamente implementados

4.3. Classes propostas

O desenho abaixo é conceitual. Não cria classes JPA nem aprova migração. Se catálogo e certificação forem separados, a atual Capacitacao deverá ser mapeada/migrada com preservação das APIs, datas, verificação e fontes. Camera, regras e incidentes exigem análise do código candidato antes de qualquer duplicação em Java. Revisão de ocorrência exige operador, decisão, justificativa e instante; regras de imutabilidade ainda serão acordadas.

Figura 6. UML conceitual proposto; nomes e relacionamentos sujeitos a decisão

4.4. DER existente

DER lógico derivado dos mapeamentos JPA. O banco em execução não foi introspectado nesta tarefa; representação UUID/boolean/timestamp é lógica, sem afirmar detalhes físicos de um dialeto SQL futuro.

Figura 7. DER atual: somente duas tabelas JPA

4.5. Modelo de dados futuro

As relações operacionais são hipótese. Uma câmera pode observar várias zonas, e uma zona pode receber várias câmeras, mas esse N:N não está aprovado. Polígonos devem ter referencial de imagem/câmera e versão. Referência a trabalhador em ocorrência é opcional e lógica entre serviços, não uma FK automática entre bancos. O Incident candidato atual exige empregado: divergência a resolver para ocorrências anônimas.

Capítulo 5. Fluxos de dados

5.1. Sincronização administrativa proposta

É uma leitura periódica/acionada do cadastro Java e atualização de uma cópia no Identity. Embora se diga Spring → Identity, o código candidato faz o pull por um cliente Python. Não transporta frames, não cadastra biometria e não identifica automaticamente ninguém. Não há prova com o Spring real desta base.

Figura 9. DFD administrativo: proposta com ponte candidata

Chave candidata: matricula → registration. Nome e ativo são sincronizados; empresa permanece no Spring. Setor/cargo não existem no Java atual. Omitidos na origem, não devem virar afirmações administrativas inventadas. Valores ausentes, desconhecidos, divergências e desativação precisam de regras explícitas.

5.2. Análise visual implementada

O usuário fornece uma imagem; FastAPI verifica tipo declarado, conteúdo, tamanho e integridade. Só então chama o detector via threadpool. Resposta válida pode conter zero pessoas. Falha retorna HTTP 503 genérico. Não gera ocorrência.

Capítulo 6. ADR-001: arquitetura híbrida e Java fora do fluxo de vídeo

Status: APROVADO pelo responsável na solicitação de documentação de 17/11/2026. Escopo: direção arquitetural; não comprovação de integração implementada.

6.1. Contexto

O projeto possui núcleo administrativo Java, visão Python e interface React. Documentos anteriores propunham passagem de imagens pelo Spring. A contribuição da Sophia apresenta módulos operacionais reutilizáveis, ainda não integrados. É necessário estabelecer fronteiras sem substituir a FastAPI validada.

6.2. Decisão

  • Spring Boot é o núcleo administrativo: trabalhadores, capacitações, futuras certificações e integrações corporativas autorizadas.

  • Python/FastAPI executa visão computacional e processamento operacional.

  • Nenhum frame de vídeo atravessa o Spring no fluxo principal.

  • Preservar YOLO11n e a FastAPI v0.3.0 atual.

  • Identity pode receber dados administrativos sincronizados fora do caminho crítico de vídeo.

  • Identity, Tracker, PPE, Fusion, Rules, Incident e Alerts são candidatos; sua adoção e os contratos de integração dependem de avaliação e validação.

  • SQL Server é possibilidade futura. A dependência JDBC existente não comprova adoção.

6.3. Consequências

Separar plano administrativo de frames reduz acoplamento e evita criar um proxy Java para transporte de vídeo. Adaptadores precisam de contratos de metadados, identificadores, autenticação, falha, repetição e atualização. Banco de ocorrência, revisão humana e zonas ainda precisam de decisões próprias.

Propostas antigas que encaminham frames por Java ficam superadas nesse ponto. Não alterar o endpoint atual para acomodar o pipeline candidato nesta fase.

6.4. Alternativas consideradas e limites

O encaminhamento de imagens pelo Spring constava no planejamento anterior e não foi escolhido como fluxo principal. Adoção integral do repositório externo, reconhecimento facial, SQL Server e nova modelagem completa em JPA não são decisões aprovadas neste ADR. Não há outros ADRs de adoção nesta revisão.

7.2. Cadastro de trabalhador

{"nome":"Pessoa fictícia","matricula":"DOC-001","empresa":"Empresa fictícia"}

Os três campos são obrigatórios, não brancos, com máximo de 255 caracteres no DTO. O serviço remove espaços nas extremidades e rejeita matrícula já existente. ativo começa true e não é campo de criação. A API atual não expõe operação de edição/desativação de trabalhador. Setor e cargo não existem nesta entidade.

Resposta de exemplo construída a partir do contrato, não captura HTTP desta tarefa:

{
  "id": "00000000-0000-4000-8000-000000000001",
  "nome": "Pessoa fictícia",
  "matricula": "DOC-001",
  "empresa": "Empresa fictícia",
  "ativo": true
}

7.3. Registro e consulta de capacitações

codigo: [A-Z0-9_-]{1,64}; nome: até 150 caracteres; realizadaEm e validaAte: LocalDate obrigatórias; verificada: boolean obrigatório; fonte: não branca até 200; verificadaPor: até 100. Realização não pode ser futura; validade não pode anteceder a realização. Registro verificado exige verificador; não verificado não deve indicá-lo. id, trabalhadorId e registradaEm são gerados/derivados pelo servidor.

Consulta usa Clock em America/Sao_Paulo e validade inclusiva no último dia. A precedência implementada é: sem registros → AUSENTE; algum registro verificado e vigente → VALIDA; senão, algum não verificado → NAO_VERIFICADA; demais → VENCIDA. Retorna autorizacaoAcesso=NAO_AVALIADA em todos esses casos.

7.4. Erros e documentação baseada em evidências

Validação de corpo e regras explícitas: 400; trabalhador não encontrado: 404; trabalhador inativo no cadastro de capacitação: 409. A configuração habilita Problem Details. Esta documentação não congela o texto integral de erros do framework nem afirma um envelope de erro idêntico ao da FastAPI.

Testes fonte: CapacitacaoApiTest, CapacitacaoServiceTest e TrabalhadorServiceTest. Cobrem persistência via contexto de teste, validade, isolamento de pessoas/códigos, duplicação e rejeição de corpos inválidos. O relatório histórico registra 20 testes Java aprovados; não reexecutados aqui. Não há Spring REST Docs configurado. Os exemplos acima são contratuais; não são snippets automaticamente capturados de requisições executadas agora.

8.1. Entrada de análise

multipart/form-data, parte obrigatória file, tipo declarado image/jpeg ou image/png. Limite exato de bytes: 5.242.880 (5 MiB), e 20.000.000 pixels. O formato real também precisa ser JPEG/PNG e passar Image.verify do Pillow. O endpoint não recebe o JSON/base64 usado pelo pipeline candidato da Sophia.

curl.exe -F "file=@imagem-autorizada.png;type=image/png" http://127.0.0.1:8000/api/v1/vision/analyze

8.2. Saída e inferência

Campos: filename, width, height, status, inference_performed, model, detections, message. Em sucesso: COMPLETED, true, yolo11n. Cada detecção contém class_id=0, class_name=person, confidence e bbox x1/y1/x2/y2 em pixels. Lista vazia é sucesso sem pessoa detectada; não significa falha.

Detector atual: YOLO11n, CPU, confiança mínima 0.40, classes=[0]. Carregamento sob demanda com cache; inferência em run_in_threadpool. Confidence é arredondada a quatro casas, coordenadas a duas. Pydantic tipa os números; os schemas atuais não impõem todos os limites geométricos ou [0,1].

Exemplo construído a partir do contrato, com zero detecções; não é nova evidência HTTP:

{
  "filename": "imagem-autorizada.png",
  "width": 640,
  "height": 480,
  "status": "COMPLETED",
  "inference_performed": true,
  "model": "yolo11n",
  "detections": [],
  "message": "Análise de imagem concluída."
}
HTTP Causa

413

Mais de 5 MiB ou 20 MP.

415

MIME declarado ou formato real não suportado.

422

Imagem inválida/corrompida ou validação automática de entrada.

503

Falha no detector/inferência/construção da resposta; mensagem genérica sem detalhes internos.

Erros explícitos retornam detail textual. Validação automática, como ausência de file, pode retornar detail como lista. Não assumir um único tipo de detail.

8.3. Testes, evidência real e consumidores

test_main.py usa monkeypatch/Mock: resultado com pessoa, vazio, falha, threadpool, disponibilidade e rejeição de imagens. Evidência histórica: 17 aprovados. Requisição real histórica: uma pessoa com confiança 0.8246. Isso não é 82.46% de acurácia nem demonstra EPIs, reconhecimento ou rastreamento operacional.

O parser React não preserva model e não restringe status a COMPLETED. Fixtures usam ANALYZED; o smoke opcional ainda espera v0.2.0. Não usar esses testes para afirmar integração real v0.3.0. A API atual deve ser preservada.

O snapshot OpenAPI é gerado por importação de main e app.openapi(), sem chamar o detector, endpoint de status ou qualquer teste/inferência. As declarações abaixo são extraídas por AST, e não mantidas como cópia manual de schemas.

Capítulo 10. Propostas, riscos e próximas decisões

10.1. Auditoria da ponte Spring / Identity

Achado no código candidato Impacto / adaptação a discutir

list_employees definido duas vezes

A versão não paginada sobrescreve a paginada; mais de 100 registros podem ser omitidos.

registration não tem unique no modelo Employee

A ponte pressupõe matrícula única; planejar detecção de duplicados e migração se houver dados.

Limites diferentes

Java aceita nome/matrícula até 255; Identity limita a 200/50. Reportar incompatibilidade sem truncar.

setor/cargo ausentes no Java

Python aceita ausência, mas cria PATIO_CARGA/OPERADOR. PATIO_CARGA não está entre os seis setores atuais; não inventar atribuição.

JWT fixo de demonstração no cliente

Externalizar configuração e renovar token; não reutilizar mecanismo de teste como autenticação definitiva.

IDs com semântica diferente

Documentar UUID Java, matrícula, UUID Identity e employee_code; resolver referências sem troca silenciosa.

As verificações externas usam Spring simulado; não há comprovação com nosso Spring real. Primeiro incremento proposto: ponte de cadastro com testes de contrato e prova HTTP real, sem vídeo, pesos de EPI ou biometria.

10.2. Decisões pendentes

  • Separação do atual registro Capacitacao em catálogo e certificação; migração e compatibilidade.

  • Fonte oficial de câmeras e ciclo de vida dos setores, evitando cadastros concorrentes.

  • Zona poligonal: coordenadas, câmera/referencial, versão e relação N:N a validar.

  • Responsável e armazenamento durável de ocorrência, evidência e revisão humana.

  • Como representar ocorrência anônima: Incident candidato exige empregado.

  • Integração entre epi_compliance e epi_rules: evitar dois vereditos concorrentes.

  • Uso do builder que infere MISSING por não detecção; avaliar visibilidade, qualidade e tempo.

  • Contratos de eventos: versão, IDs, sessão, timestamp, repetição, atraso e expiração.

  • Autenticação entre serviços, falhas parciais, URLs e portas de desenvolvimento/produção.

  • Banco durável: H2 atual é volátil; SQL Server/PostgreSQL são possibilidades não decididas.

10.3. Validações mínimas para uma futura implementação

Ponte: execução repetida sem duplicar, mais de 100 funcionários, concorrência, matrícula duplicada, campos longos, valores ausentes/inválidos, inativo, origem indisponível, falha parcial, token expirado, registro ausente sem exclusão e preservação de dados operacionais. O Java atual não expõe atualização de trabalhador; testar essas transições por contrato não equivale a tê-las disponíveis na API.

Visão: modelo certo/classes reais, peso disponível, caixa válida, perda de visibilidade, enquadramento cortado, confiança baixa, estado indeterminado, expiração e não conversão automática de não detecção em infração. Não usar nosso modelo person-only para inferir ausência de EPIs.

Revisão: operador autenticado, motivo obrigatório, histórico preservado, idempotência, referência de evidência e evento sem identidade quando necessário. Esses são critérios propostos, não testes já executados.

10.4. Plano incremental sugerido

  1. Corrigir contratos da ponte no projeto responsável, com ambiente isolado.

  2. Demonstrar Spring real → sincronizador → Identity real com dados fictícios.

  4. Avaliar modelos/serviços Python sem substituir YOLO11n ou alterar a API existente.

  5. Integrar metadados e revisão após testes; manter frames no processamento Python.
